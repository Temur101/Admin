# План исправления ошибок LeadCatch & QuickBook

Дата: 11 октября 2026. База анализа: коммит `4e78bcc7e198d29c6917d24c2d1bce2f72f44ed2`.

Документ дополняет [исходный план](../implementation_plan.md), не заменяя его.
Цель — устранить ошибки доступа, потери данных и конкурентных операций перед
этапом 7 (Admin API). Новые функции админки, шаблоны и деплой сюда не входят.
Работа выполняется по [AGENTS.md](../AGENTS.md).

## Статус и исходные проверки

Все пункты ниже **запланированы, исправления ещё не выполнены**. Замечания основаны
на чтении кода; для каждого сначала нужен воспроизводящий тест. Там, где последствия
требуют дополнительного подтверждения, это указано отдельно.

В предыдущем прогоне прошли 88 unit-тестов в 6 наборах, ESLint, dependency-cruiser,
Knip, anti-mock, сборки contracts и admin. Backend typecheck был заблокирован
отсутствующим Prisma Client: загрузка checksum с `binaries.prisma.sh` получила 403.
Интеграционные тесты и реальный Telegram в облачной среде не проверены. Эти результаты
не являются доказательством исправления перечисленных ошибок.

Приоритеты: P0 — доступ к данным и безопасность тестов; P1 — корректность данных,
доставка и запуск; P2 — согласованность кода и воспроизводимость разработки.

## Порядок работы

`B00 → B01 → B02 → B03 → B04 → B05 → B06 → B07 → B08 → B09`.

B00 обеспечивает безопасные проверки. B02 нужен для проверки отзыва приглашений
и статусов без перезапуска. B03 создаёт основу восстановления обработки; B06 использует
согласованный механизм задач. B07 зависит от доставки и новых правил биллинга.
Независимые проверки допустимо выполнять отдельно, сохраняя приоритеты.

## B00 — Безопасная тестовая среда (P0)

- **Файлы:** `apps/server/test/*.test.ts`, `vitest.config.ts`,
  `apps/server/src/core/prisma.ts`, `core/env.ts`, `.env.example`, скрипты пакетов.
- **Проблема:** общие таблицы, `flushdb()` и fallback на `REDIS_URL`; несколько файлов
  содержат пароль подключения. Параллельные наборы могут удалять данные друг друга.
  Проверить также fallback Prisma на основную БД.
- **Работа:** обязательные отдельные TEST-подключения, запрет очистки основной БД,
  удаление встроенных credentials, общий test setup. Сначала допустим последовательный
  запуск интеграционных файлов; unit-тесты остаются независимыми. Подготовить тестовые
  PG/Redis, миграции и Prisma Client. Проверить доступ к `binaries.prisma.sh`, сохраняя
  TLS/checksum. Если доступ закрыт — зафиксировать блокер.
- **Проверки:** без TEST-переменных отказ до соединения/очистки; совпадение test
  и основной цели отклоняется; контрольные данные dev не затрагиваются. Полный набор
  дважды проходит без взаимного удаления фикстур.
- **Готово:** интеграционные проверки воспроизводимы и защищены от случайной очистки
  основной БД/Redis. Если встроенный пароль реально используется, его заменяет владелец
  через защищённую конфигурацию, без публикации значения.

## B01 — Права во всех действиях ботов (P0)

- **Файлы:** `bots/shared/handlers.ts`, `user-service.ts`,
  `bots/quickbook/quickbook-composer.ts`, `booking-service.ts` (в `apps/server/src`).
- **Проблема:** `admin:leads` не проверяет роль; отмена принимает только ID записи,
  без текущего бота и владельца. Подтверждение отвечает текстом без проверки записи.
- **Работа:** единая проверка актуального администратора; операции с бронью ограничить
  `botId` и владельцем. Проверять права после отзыва роли. Проверить остальные callback.
- **Проверки:** обычный пользователь и бывший администратор не получают лиды; чужая
  запись и запись другого бота не изменяются; старые кнопки не дают прав; собственная
  отмена работает, повторная отмена безопасна.
- **Готово:** положительные и отрицательные сценарии проходят через обработчики.
  Не добавлять новый бизнес-статус подтверждения без требования.

## B02 — Актуальность кешей и метаданных (P1)

- **Файлы:** `gateway/bot-pool.ts`, `tenant-resolver.ts`, `types.ts`,
  `bots/shared/admin-menu.ts`, `payment-service.ts`, `workers/subscription-worker.ts`.
- **Проблема:** grammY-экземпляр замыкает первоначальный `resolved`; очистка Redis
  не обновляет его. Статусы, настройки и приглашение остаются старыми в LRU.
- **Работа:** отделить кеш транспорта от актуальных метаданных каждого update;
  согласовать инвалидирование всех слоёв после commit. Для прав/маскирования обеспечить
  актуальные данные. Общее изменяемое поле перед `await` не использовать без защиты
  от параллельных запросов. Проверить реальный Telegram bot ID вместо вычисления из UUID.
- **Проверки:** прогреть кеш, изменить подписку/приглашение/settings и повторить update
  в том же процессе. Старое приглашение отвергается, контакты маскируются, новый сценарий
  применяется. Проверить параллельные запросы, сбой инвалидации и адресованные боту команды.
- **Готово:** изменения действуют без рестарта/вытеснения; проверены оба слоя кеша.

## B03 — Приём webhook без потери сообщений (P1)

- **Файлы:** `gateway/webhook-handler.ts`, `deduplicator.ts`, `bot-pool.ts`,
  Prisma-схема/миграции и модуль обработки задач при необходимости.
- **Проблема:** дедупликация записывается до проверки перегрузки; повтор после 429
  отбрасывается. После 200 обработка существует только в `setImmediate`.
- **Работа:** выбрать сохраняемый inbox/очередь (предпочтительно на уже используемом
  PostgreSQL), атомарный приём с уникальным `(botId, updateId)`, состояния обработки,
  lease и ограниченные повторы. Подтверждать приём после сохранения. Сериализовать
  конфликтующие изменения одной сессии. Бизнес-записи защищать от повтора после
  частичного успеха. Выбор механизма и гарантии записать в техническом решении.
- **Проверки:** перегрузка → повтор; дубли одновременно; рестарт после приёма;
  сбой после записи лида/брони; недоступность БД/Redis; сообщения одного пользователя
  одновременно; одинаковые update ID разных ботов.
- **Готово:** принятые сообщения восстанавливаются; повтор не создаёт второй лид,
  бронь или продление; очередь/конкуренция ограничены. Непринятый запрос не считается
  обработанным. Ограничения повторной отправки внешних сообщений описаны.

## B04 — Пересекающиеся бронирования (P1)

- **Файлы:** `bots/quickbook/booking-service.ts`, `slot-lock.ts`, `slot-generator.ts`,
  Prisma-схема и новая миграция; существующие миграции не переписывать.
- **Проблема:** индекс/lock защищают одинаковое начало, не пересечение интервалов.
  При сохранении проверяется наличие услуги/ресурса, но не вся допустимость слота.
- **Работа:** атомарный запрет пересечения активных интервалов ресурса в БД
  (exclusion constraint либо сериализация на ресурсе с повторной проверкой).
  Проверять расписание, длительность, соответствие услуги ресурсу, прошлое время,
  перерыв и горизонт записи. Lock получает уникальный ID захвата.
- **Проверки:** 50 запросов одного слота; параллельные 10:00–11:00 и 10:30–11:00;
  соседние интервалы, разные ресурсы/боты, отменённая бронь, устаревшая кнопка,
  истечение lock и повторный захват тем же пользователем.
- **Готово:** пересечения невозможны при конкурентной записи через сервис; соседние
  допустимы. Миграция выявляет существующие пересечения и не удаляет их автоматически.

## B05 — Конкурентный биллинг и откат (P1)

- **Файлы:** `bots/shared/payment-service.ts`, `subscription.ts`, `receipt-handlers.ts`,
  Prisma-схема/миграции при необходимости, `test/payment-receipt.test.ts`.
- **Проблема:** read-then-write PENDING не защищает параллельную проверку; откат
  к `prevPaidUntil` может отменить независимое продление. Повторное одобрение может
  повторно отправить уведомление.
- **Работа:** сериализация изменений подписки, атомарный переход чека, единая логика
  переходов. Учёт начислений/отмен сохраняет другие оплаты независимо от порядка
  рассмотрения. Сохранить оптимистичную активацию и правила попыток; уведомления
  планировать после commit с ключом идемпотентности события.
- **Проверки:** approve/approve, reject/reject, approve/reject одновременно; две
  одновременные отправки; чеки A/B отклонены в обоих порядках; один одобрен, второй
  отклонён; продление между отправкой и рассмотрением; прежний активный срок,
  первая/вторая ошибка, повтор webhook.
- **Готово:** один терминальный исход на чек, однократные начисления/отмены, сохранение
  независимых оплат. Автомат подписок проверен также через рабочий сервис.

## B06 — Напоминания с восстановлением (P1)

- **Файлы:** `workers/booking-reminder-worker.ts`, `bots/quickbook/booking-service.ts`,
  хранилище задач/миграции при необходимости.
- **Проблема:** задача удаляется и `reminderSent` выставляется до отправки; ошибка
  Telegram теряет напоминание. Сбой Redis при создании брони теряет планирование.
- **Работа:** сохранять задачу вместе с бронью либо восстанавливать из БД; claim/lease,
  отметка успеха после ответа Telegram, backoff и предел попыток. Проверять отмену
  перед отправкой. Пакетные выборки; определить судьбу просроченных задач после простоя.
- **Проверки:** ошибка Telegram → успешный повтор; Redis недоступен при бронировании;
  рестарт в разных точках; отмена; два воркера; истечение lease.
- **Готово:** временный сбой не теряет задачу, исчерпанные попытки наблюдаемы; возможный
  дубль при сбое после внешней отправки указан как ограничение API.

## B07 — Запуск и остановка фоновых задач (P1)

- **Файлы:** `src/index.ts`, оба `workers`, жизненный цикл Redis/Prisma.
- **Проблема:** воркеры экспортируются, но приложение не запускает их по расписанию;
  lock со значением `1` удаляется без проверки владельца. Проверить гонку истечения
  подписки с продлением.
- **Работа:** scheduler при запуске сервера с внедряемыми зависимостями, остановкой
  и ожиданием задач; уникальные lease и защита от перекрытия. EXPIRED выставляется
  условно по актуальным срокам. Разделить liveness/readiness: `/health` с постоянным
  `ok` не доказывает доступность зависимостей.
- **Проверки:** обычный запуск, без ручного вызова worker, запускает обработку;
  shutdown не оставляет таймеров; длинный tick не удаляет чужой lock; продление
  во время tick не становится EXPIRED; readiness отражает отказ зависимости.
- **Готово:** smoke жизненного цикла подтверждает работу обеих задач.

## B08 — Сборка, типизация и единые правила в коде (P2)

- **Файлы:** package/tsconfig, `bots/shared/*`, `bots/leadcatch/quiz-flow.ts`,
  `gateway/bot-pool.ts`, README и документация окружения.
- **Наблюдения:** `start` ожидает `dist/index.js`, но `rootDir: "."` с входом
  `src/index.ts` предполагает `dist/src/index.js`; подтвердить чистой сборкой.
  Есть `as any` с отключением линтера, фиксированные цены кнопок, дублирование
  переходов подписки (устраняется в B05).
- **Работа:** согласовать выход сборки/entrypoint; типизировать параметры Telegram,
  получать цены из настроек; реальные botInfo и адресованные команды проверить в B02.
  Документировать проверенные версии Node/pnpm/PG и порядок генерации/сборки.
  Чистый DAG unit-тест не должен требовать секреты всего приложения из-за barrel-импорта.
- **Проверки:** чистая установка → генерация → build → production start; изменение
  тарифа отражается в кнопке/платеже; unit-тесты без сервисов/рабочих секретов;
  typecheck/lint/depcruise/knip/check-mocks проходят без новых обходов.
- **Готово:** воспроизводимый запуск и согласованный пользовательский результат.
  Исходный план сохраняется, расхождения описываются отдельно.

## B09 — Итоговая проверка и возврат к этапу 7

- Полный `pnpm verify` с отдельными тестовыми PostgreSQL/Redis.
- Миграции на чистой БД и тестовой копии прежней схемы.
- LeadCatch и QuickBook через webhook с Telegram-адаптером: диалог → сохранение →
  уведомление → чек → решение → истечение → маскирование.
- Перезапуск, перегрузка, отзыв прав и конкуренция из B01–B07.
- Обычный запуск собранного сервера и автоматическая работа воркеров.
- Реальный Telegram — отдельный smoke после предоставления тестовых ботов.
  Его отсутствие не выдавать за успех и не смешивать с проверками адаптера.
- Для каждого B-пункта записать файлы, команды, результаты, миграции и ограничения.
  «Исправлено» означает воспроизведение до изменения и успешный регрессионный тест после.

К этапу 7 возвращаемся после B00–B07, устранения блокирующего production start из B08
и успешных обязательных проверок B09. Остальные P2 допускают явный перенос с описанием
риска. Реальный Telegram проверить до эксплуатации. Неподтверждённую гипотезу закрывать
результатом исследования, а не фиктивным исправлением.

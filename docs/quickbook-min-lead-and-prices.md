# QuickBook: Минимальное время до онлайн-записи и управление ценами услуг

Документ описывает архитектуру, порядок обновления и ограничения отката для функций:

1. Управление минимальным временем до онлайн-записи (`minLeadMinutes`, минимум 60 минут).
2. Управление ценами существующих услуг (`priceUzs`) через Telegram (только роль `OWNER`) и веб-админку с отложенным вступлением в силу со следующего рабочего дня (`00:00 Asia/Tashkent`).
3. Фиксация согласованной цены (`Booking.priceUzs`) в момент подтверждения записи.

---

## 1. Технические решения

### 1.1. Хранение действующих и ожидающих настроек

- Действующие значения хранятся в `Bot.settings`:
  - `minLeadMinutes?: number` (целое число $\ge 60$; для старых ботов до наступления первого запланированного рабочего дня поле отсутствует, сохраняя прежнее поведение).
  - `services[].priceUzs: number` (целое число $\ge 0$).
- Ожидающие изменения и история хранятся в таблице `BotSettingChange`:
  - `kind`: `MIN_LEAD` | `SERVICE_PRICE`
  - `targetId`: `""` для `MIN_LEAD`, `serviceId` для `SERVICE_PRICE`
  - `oldValue`, `newValue`: прежнее и новое значение
  - `effectiveAt`: `TIMESTAMPTZ` (`00:00:00+05:00` обещанного рабочего дня в `Asia/Tashkent`)
  - `status`: `PENDING` | `APPLIED` | `REPLACED` | `CANCELLED`
  - `createdByTgId`, `createdByAdminId`, `resolvedAt`, `resolvedByTgId`, `resolvedByAdminId`, `resolution`
- Частичный уникальный индекс `bot_setting_change_pending_uq` на `(botId, kind, targetId) WHERE status = 'PENDING'` гарантирует, что у одной настройки может быть не более одного ожидающего изменения, а изменения разных услуг и `MIN_LEAD` не перезаписывают друг друга.

### 1.2. Надёжная активация и защита от гонок

- Все изменения настроек и ожидающих значений бота сериализуются блокировкой строки `SELECT id FROM "Bot" WHERE id = $1 FOR UPDATE` (`lockBotRow`).
- При чтении конфигурации (`loadEffectiveSettings`, `loadEffectiveConfig`) поверх `Bot.settings` автоматически накладываются (`overlayChanges`) все записи `BotSettingChange` со статусом `PENDING` и `effectiveAt <= now`. Благодаря этому сразу после `00:00` (в том числе после простоя сервера и до срабатывания фонового воркера или инвалидации кеша) в силу вступают новые значения.
- Фоновый планировщик (`BackgroundWorkerScheduler`) переводит наступившие `PENDING`-изменения в `APPLIED`, точечно обновляя только целевые поля `Bot.settings` и сбрасывая кеш `TenantResolver` / Redis. Операции изменения настроек также сначала применяют уже наступившие значения.
- Оформление и перенос записи берут разделяемую блокировку строки бота, затем блокировки календаря и мастера. После ожидания всех блокировок повторно читаются действующие настройки и серверное время; изменение настроек не может одновременно перезаписать проверяемую конфигурацию. Согласованная цена повторно сверяется перед созданием записи.
- Первоначальное включение обязательного часового минимума сохраняется до назначенной даты. При отмене большего первоначального срока остаётся включение одного часа на ту же дату. Изменение с уже наступившей датой нельзя отменить как ожидающее.
- Полная веб-форма сохраняется с версией всей конфигурации и ожидающих изменений. При конфликте возвращается `STALE_SETTINGS`: данные нужно обновить. Версия редактируемой формы не подменяется фоновой загрузкой новых данных.
- При удалении услуги через веб-админку её ожидающее изменение цены переводится в `CANCELLED` (`resolution = "service removed"`), и активация никогда не восстанавливает удалённую услугу.

### 1.3. Фиксация цены в `Booking`

- В таблицу `Booking` добавлен столбец `priceUzs INTEGER NULL` с ограничением `Booking_priceUzs_nonneg CHECK ("priceUzs" IS NULL OR "priceUzs" >= 0)`.
- Для существующих (исторических) записей сохраняется `NULL` — неизвестная историческая стоимость не подменяется ни нулём, ни текущим прайсом.
- При показе экрана подтверждения (клиенту или владельцу при ручной записи) цена фиксируется в сессии (`session.priceUzs`) и передаётся как `expectedPriceUzs` в `createBooking`. Если прайс успел измениться до нажатия кнопки подтверждения, `createBooking` возвращает `PRICE_CHANGED`, старый токен подтверждения сбрасывается и пользователю показывается обновлённый итог для повторного подтверждения.

## 2. Порядок обновления (Deployment)

1. Сделать резервную копию PostgreSQL (`pg_dump`), директории `uploads/` и файла `.env` (сохранив неизменным `TOKEN_ENCRYPTION_KEY`).
2. Остановить процесс сервера (`@lcqb/server`).
3. Установить зависимости и сгенерировать Prisma Client:
   ```bash
   pnpm install --frozen-lockfile
   pnpm --filter @lcqb/server prisma:generate
   ```
4. Применить миграции БД:
   ```bash
   pnpm --filter @lcqb/server prisma:migrate:deploy
   ```
   Будет применена миграция `20261101190000_min_lead_and_price_changes`.
5. Собрать пакеты и приложения:
   ```bash
   pnpm build
   ```
6. Запустить сервер и проверить готовность (`GET /health/ready`). При старте планировщика функция `ensureInitialMinLead` автоматически и идемпотентно запланирует включение `minLeadMinutes = 60` со следующего рабочего дня для всех ранее созданных ботов QuickBook, у которых это поле ещё не задано.

## 3. Ограничения отката (Rollback)

1. **Код без отката БД (безопасно):**
   Новые изменения схемы (`Booking.priceUzs NULL`, таблица `BotSettingChange`, поле `minLeadMinutes` в JSON `Bot.settings`) обратно совместимы со старой версией кода на уровне чтения таблиц `Bot` и `Booking`. Однако при откате кода на предыдущий коммит перестанут учитываться ожидающие изменения из `BotSettingChange` и ограничение `minLeadMinutes`.
2. **Откат миграции БД (требует внимания к данным):**
   Удаление таблицы `BotSettingChange` и столбца `Booking.priceUzs` приведёт к необратимой потере истории запланированных изменений цен/сроков и сохранённых цен в оформленных после обновления записях. Для полного отката БД необходимо восстанавливать дамп PostgreSQL, созданный на шаге 1 перед обновлением.

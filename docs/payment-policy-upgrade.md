# Обновление политики оплаты

Новые чеки остаются PENDING до решения платформенного администратора. Отправка текста или изображения не продлевает доступ. Одобрение продлевает текущий действующий оплаченный срок; повторное одобрение ничего не начисляет. Отклонение нового чека не вычитает независимо оплаченный срок. Живой пробный период сохраняется после первого отклонения.

## Совместимость со старыми чеками

Миграция `20261030190000_payment_approval_gate` помечает существующие PENDING как `optimisticGranted=true`. Они уже получили доступ по прежним правилам. Их одобрение не начисляет месяцы повторно. При отклонении отменяется записанный старый грант; независимое продление сохраняется. Новые чеки имеют `optimisticGranted=false`.

В тестовой PostgreSQL проверено применение настоящего SQL миграции: старый PENDING получает true, APPROVED/REJECTED — false. Отдельные интеграции проверяют одобрение/отклонение старого гранта, конец месяца и независимое продление.

## Порядок выкладки

1. Сделать резервную копию PostgreSQL, uploads и сохранить ключ шифрования токенов в защищённом хранилище. Проверить восстановление копии в отдельную базу.
2. Включить технический перерыв и остановить старый процесс приложения/воркеры, чтобы чеки не создавались между миграцией и обновлением кода.
3. Установить зависимости по lockfile, сгенерировать Prisma Client и применить миграции через `prisma migrate deploy` с production-конфигурацией.
4. Собрать и запустить новую версию. Не запускать старую и новую политику оплаты одновременно.
5. Проверить `/health/ready`, ожидающие чеки, очередь уведомлений и клиентский сценарий в Telegram.
6. После приёмки выключить технический перерыв. Ошибки доставки контролировать в диагностике бота.

Обратная выкладка старого кода после изменения политики требует отдельного плана: старый код не учитывает новые ожидающие чеки без выданного доступа. Автоматическое удаление колонок или очистка платёжных данных не допускается.

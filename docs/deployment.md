# Размещение проекта: сервер, админка, адрес и данные

Это руководство объясняет, что нужно подготовить для первого серверного запуска. Оно не означает, что VPS уже настроен. В текущем репозитории нет готовых Dockerfile/Compose, расписания бэкапов и конфигурации HTTPS. Очистка репозитория не заменяет этот этап.

## Рекомендуемая схема для первых клиентов

Один Linux VPS обслуживает сервер Telegram-ботов, PostgreSQL, Redis, файлы чеков и статическую сборку админки. Веб-сервер, например Nginx, принимает HTTPS: выдаёт файлы React, а запросы `/api` передаёт внутреннему Node.js-серверу.

Браузер видит админку и API по одному адресу. Так проще обеспечить вход, обновление сессии и загрузку чеков. React после сборки — набор файлов; отдельный VPS для админки не нужен. Для небольшой первой нагрузки ориентир — 2 vCPU, 2–4 ГБ RAM и SSD от 30–40 ГБ с возможностью увеличить объём. Это стартовая оценка, а не подтверждённый нагрузочным тестом предел.

На первом запуске можно сохранить polling: сервер сам обращается к Telegram. Это не требует публичного адреса вебхука. Платный домен не нужен самим ботам, а клиенты продолжают пользоваться их обычными Telegram-именами.

## Можно ли админку разместить на Vercel

Да. Там можно разместить статическую сборку React и использовать выданный проекту адрес `*.vercel.app`, не покупая собственный домен. Боты, база, Redis и фоновые задачи всё равно должны работать на постоянно доступном сервере; публикация одной админки не запускает существующий backend.

Для этого проекта есть особенность: браузер вызывает относительные адреса `/api/v1/...`, а вход использует защищённую HttpOnly cookie обновления с `SameSite=Strict`. Сейчас проксирование существует только в dev-сервере Vite и не переносится автоматически в production.

При отдельной админке на Vercel нужно настроить внешнее проксирование `/api` на HTTPS-адрес backend, сохранив путь, заголовки авторизации, cookies и ответы сервера. Тогда для браузера запросы остаются на адресе админки. Простое перенаправление браузера на чужой API-домен не заменяет прокси: для прямых cross-site запросов текущая строгая cookie не подходит. Менять её защиту ради быстрого запуска не нужно.

Также потребуется:

- Настроить сборку monorepo, включая общий пакет contracts; публиковать результат `apps/admin/dist`.
- Обеспечить fallback React Router для страниц интерфейса, сохранив отдельную обработку `/api` перед ним.
- Указать точный production-адрес админки в `ADMIN_ORIGIN` backend.
- Проверить вход, автоматическое обновление токена, выход и просмотр файлов через выбранный прокси.
- Не кешировать персонализированные API-ответы на CDN.
- Хранить токены ботов, пароли базы и ключи JWT/шифрования только на backend, не в переменных сборки фронтенда.

Vercel поддерживает [внешние rewrites](https://vercel.com/docs/routing/rewrites). При этом [Hobby предназначен для личного некоммерческого использования](https://vercel.com/docs/plans/hobby): для платной платформы нельзя заранее считать этот тариф подходящим. Условия тарифа нужно учитывать до выбора Vercel для production. Бесплатный адрес сайта и бесплатное коммерческое размещение — разные вопросы.

Для первых клиентов вариант с одним VPS обычно проще: один адрес, одна конфигурация HTTPS и одна точка обновления. При необходимости админку можно вынести позже.

## Как обойтись без покупки домена

Админке нужен адрес с рабочим HTTPS. Возможны такие варианты:

1. **Служебное имя от VPS-провайдера или бесплатный поддомен.** Нужно заранее проверить, что провайдер его действительно предоставляет, адрес стабилен и для него можно выпустить сертификат.
2. **HTTPS непосредственно на публичном IP VPS.** Let's Encrypt поддерживает [сертификаты для IP-адресов](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability). Они короткоживущие — около шести дней, поэтому нужен совместимый ACME-клиент, полностью автоматическое продление и контроль ошибок. При смене IP сертификат настраивают заново.
3. **Приватный доступ к админке.** Если интерфейс нужен только владельцу, можно закрыть его от интернета и подключаться через VPN или защищённый туннель. Доверенный HTTPS и поведение защищённых cookies нужно согласовать с этим способом доступа; обычный HTTP по публичному IP не является готовым production-вариантом.

Если используется Vercel, его адрес решает вопрос адреса фронтенда. Для связи Vercel с отдельным backend всё равно нужен доступный HTTPS-адрес backend. Собственный домен можно приобрести позднее; для запуска он не является обязательной покупкой.

## Что должно работать на сервере

**Приложение.** Собранный Node.js-сервер работает постоянно и запускается после перезагрузки VPS. Режим наблюдения `tsx watch` предназначен для разработки. Фоновые задачи подписок, напоминаний и доставки запускаются вместе с сервером.

**PostgreSQL.** База находится на постоянном диске или Docker volume. Пересоздание контейнера приложения не должно удалять заявки, записи и настройки. Все существующие миграции сохраняются; обновление схемы выполняют перед запуском новой версии кода.

**Redis.** Нужен для сессий и блокировок. Его тоже настраивают как постоянный сервис с продуманным сохранением состояния. При переносе состояние Redis рассматривают отдельно: потеря сессий может завершить незаконченные диалоги, хотя подтверждённые записи хранятся в PostgreSQL.

**Загрузки.** `uploads` хранится вне временного слоя контейнера приложения. Именно здесь находятся файлы чеков; копии одной базы для их восстановления недостаточно.

**Вход и секреты.** Конфигурация production хранится на сервере вне Git. При переносе существующих ботов обязательно сохранить прежний `TOKEN_ENCRYPTION_KEY`: без него нельзя расшифровать токены из базы. Пароли и другие секреты не помещают в образ Docker или сборку React.

**Веб-сервер.** Принимает HTTPS, обслуживает админку и проксирует API. PostgreSQL и Redis не публикуют в интернете. Внутренний порт Node.js также не открывают напрямую, когда перед ним есть HTTPS-прокси. SSH ограничивают административным доступом и используют ключи.

Docker Compose может объединить эти компоненты в понятную конфигурацию. Для него ещё нужно подготовить образы, внутреннюю сеть, постоянные тома, проверки готовности, порядок миграций и автозапуск. Docker упрощает эксплуатацию, но не создаёт автоматически бэкапы и не гарантирует восстановление данных.

## Резервные копии и контроль работы

До первых клиентов нужно настроить автоматические копии PostgreSQL и `uploads`, а также защищённое хранение конфигурации и ключа шифрования. Хранить несколько последних версий; как начальный режим подходят ежедневные копии и отдельная копия перед обновлением.

Хотя бы одна копия должна находиться вне VPS: в другом хранилище или на другом устройстве. Файл копии на том же сервере и Docker volume не защищают от потери всего диска. Копии содержат данные клиентов и секреты, поэтому доступ к ним ограничивают, а при передаче в стороннее хранилище используют шифрование.

Нужно восстановить копию в отдельную базу и проверить данные и файлы, не перезаписывая рабочую базу. Автоматические копии считаются подтверждёнными после такой проверки. Сохранённая при очистке копия файлов репозитория не является бэкапом пользовательской базы.

Дополнительно настраивают уведомления о недоступности сервиса, ошибках доставки, неуспешных бэкапах и продлении сертификатов; ограничивают объём логов и контролируют свободное место. Автоперезапуск процесса и проверка `/health/ready` решают разные задачи: нужен и работающий процесс, и доступные база/Redis.

## Как перенести работающий проект с ноутбука

1. Подготовить VPS, хранилища, адрес админки, HTTPS и новую конфигурацию. Заранее проверить сборку и восстановление на тестовой копии.
2. На время окончательного переноса остановить старый сервер ботов. Сделать согласованную свежую копию базы и загрузок, сохранить конфигурацию и ключ шифрования. Не оставлять старый polling одновременно с новым.
3. Восстановить данные на VPS, применить миграции и запустить один экземпляр обработки ботов. Проверить правильные каталоги данных и реальный Telegram-транспорт.
4. Проверить админский вход и обновление сессии, опрос и обработку заявки, запись/перенос/отмену и уведомления, затем применение отложенных настроек в назначенную дату.
5. Проверить поведение после перезагрузки VPS и восстановление резервной копии. Старую копию данных не удалять, пока перенос не подтверждён.

После этого ноутбук не должен оставаться включённым ради ботов: их обслуживает VPS. Ботов в BotFather пересоздавать не нужно — сохраняются токены и данные подключения.

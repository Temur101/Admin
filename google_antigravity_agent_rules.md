# Инструкции и Правила Разработки для Google Antigravity

## 1. Роль и Тональность
Ты выступаешь в роли **Senior Backend/Fullstack Инженера** с жестким фокусом на надежность, безопасность и чистоту архитектуры.
*   **Никакой "ИИшности":** Запрещены пустые вступительные фразы ("Конечно, я с радостью помогу вам...", "Отличный выбор технологии..."), избыточные эпилоги и пространные резюме. 
*   Отвечай сухо, профессионально и по существу, сопровождая код только необходимыми архитектурными комментариями.
*   Не строй предположений о бизнесе сверх того, что описано в `system_architecture.md`.

## 2. Политика работы с данными и моками (Strict Anti-Mock Policy)
*   **Запрещены фиктивные заглушки в боевой логике:** Никаких захардкоженных массивов `const fakeLeads = [...]` или симуляций БД через `setTimeout`.
*   Все операции с базой данных, FSM и внешними API пишутся сразу под реальные клиенты:
    *   PostgreSQL: через реальный пул соединений с параметризованными SQL-запросами или проверенный ORM (Drizzle/Prisma/SQLAlchemy).
    *   Redis: через реальный клиент с обработкой разрыва соединения.
*   **Исключение (когда мок неизбежен):** 
    *   Если локально отсутствует внешний API (например, эмуляция банковского шлюза или отправка Telegram-сообщений во время изолированных unit-тестов), мок выносится **строго за интерфейс/адаптер**.
    *   Переключение между моком и реальным драйвером должно происходить **в 1 клик через переменную окружения**:
        ```typescript
        // Пример обязательного паттерна при необходимости мока:
        const notificationService = process.env.USE_MOCK_NOTIFIER === 'true'
            ? new MockTelegramNotifier()
            : new RealTelegramBotNotifier(botToken);
        ```

## 3. Архитектурные ограничения и безопасность
1.  **Лимиты ресурсов VPS:**
    *   Оперативная память строго ограничена (2 GB на всю систему). Избегай утечек памяти, не держи тяжелые объекты и FSM-состояния в оперативной памяти процессов Node.js/Python. Все временные состояния живут строго в Redis с TTL.
2.  **Обработка Webhook:**
    *   Хэндлер вебхука Telegram обязан отдавать статус `200 OK` до начала выполнения тяжелых операций (генерация картинок, запись в аналитику).
3.  **Идемпотентность и Race Conditions:**
    *   Операции бронирования слотов в QuickBook обязаны использовать Redis-блокировки (`SET resource_key lock_id NX EX 60`) для защиты от одновременной записи.
    *   Обработка одного и того же `update_id` от Telegram должна быть идемпотентной.
4.  **Безопасность файлов:**
    *   Загружаемые скриншоты чеков валидируются по MIME-типу (`image/jpeg`, `image/png`) и размеру (макс. 5 МБ).
    *   Имена файлов генерируются как случайные UUIDv4. Запрещено использовать оригинальные имена файлов от пользователей во избежание Path Traversal.

## 4. Стандарты кода
*   **TypeScript / Python:**
    *   TypeScript: режим `strict: true`. Никаких типов `any`. Все структуры запросов/ответов строго типизированы через DTO/Zod-схемы.
    *   Python: обязательное использование Pydantic v2 и Type Hints везде.
*   **React (Admin Dashboard):**
    *   Функциональные компоненты, хуки, Tailwind CSS.
    *   Никаких спагетти-компонентов на 500 строк: разделять UI-виджеты, API-клиент и слой состояния.
*   **Работа с изменениями:**
    *   Никогда не обрезать код фразами `// TODO: допишите остальное сами`. Генерируй завершенные, синтаксически корректные модули.
    *   Не трогать и не рефакторить файлы, не относящиеся к текущей задаче, без прямого указания.

## 1. Введение и цели аудита

### 1.1. Контекст системы
Платформа представляет собой мультитенантный Telegram SaaS Engine, предназначенный для создания и обслуживания ботов двух типов:
1. **LeadCatch**: диалоговые опросники (квалификация лидов) на основе ориентированного ациклического графа (DAG) длиной от 3 до 5 шагов.
2. **QuickBook**: модуль онлайн-записи клиентов на услуги к конкретным специалистам/ресурсам (мастера, столики, кабинеты) с выбором слотов времени, защитой от овербукинга и напоминаниями.

Система работает в едином монолитном процессе Node.js (Fastify 5 + grammY + Prisma 6 + ioredis), обслуживая множество независимых тенантов (бизнесов) и ботов с изоляцией контекста, сессий и данных.

### 1.2. Цели аудита
- Провести комплексную инвентаризацию репозитория и валидацию архитектурных ограничений.
- Подтвердить безопасность, отсутствие утечек контекста между тенантами (cross-tenant leakage) и строгость разграничения ролей.
- Оценить устойчивость к конкурентным нагрузкам (гонки за слоты бронирования, дублирование вебхуков, фрод с чеками оплаты).
- Проанализировать React-панель управления платформой (`apps/admin`) и согласованность контрактов данных (`@lcqb/contracts`).
- Оценить готовность продукта к первому платному пилоту на реальных клиентах, выявить блокеры и составить воспроизводимую матрицу доказательств.

## 3. Переменные окружения и конфигурация

Конфигурация бэкенда строго валидируется при старте через `zod` (`apps/server/src/core/env.ts`):
- **Сетевые параметры:** `PORT` (8000), `HOST` ("127.0.0.1"), `NODE_ENV`, `PUBLIC_BASE_URL` (HTTPS URL для вебхуков), `BOT_MODE` ("polling" или "webhook"), `ADMIN_ORIGIN` ("http://localhost:5173").
- **Базы данных:** `DATABASE_URL` (PostgreSQL), `REDIS_URL` (Redis), а также обязательные тестовые URL: `TEST_DATABASE_URL` и `TEST_REDIS_URL`.
- **Безопасность тестового окружения (B00):** Защита в `apps/server/test/helpers/test-env.ts` жестко блокирует запуск тестов, если имя тестовой БД не содержит `test` или если тестовые URL совпадают с боевыми/dev.
- **Криптография:** `TOKEN_ENCRYPTION_KEY` (32 байта Base64 для шифрования токенов ботов алгоритмом AES-256-GCM в БД), `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` (TTL 15m / 7d).
- **Суперадминистратор:** `SUPERADMIN_EMAIL`, `SUPERADMIN_PASSWORD` (создается/обновляется при старте через `ensureSuperAdmin` с хешированием Argon2).
- **Лимиты VPS (2 GB RAM):** `connection_limit=10` в Prisma, `enableOfflineQueue: false` в Redis, `BOT_INSTANCE_CACHE_SIZE=200` (LRU-кэш ботов в памяти), `WEBHOOK_MAX_INFLIGHT=500` (ранний возврат 429 при перегрузке).

## 5. Изоляция тенантов и жизненный цикл обработки событий

### 5.1. TenantResolver и кэширование
- Каждый бот идентифицируется по 64-символьному SHA-256 хешу токена (`botTokenHash`).
- Маршрут вебхука: `/api/v1/tg/webhook/:botTokenHash`.
- `TenantResolver` резолвит метаданные бота через двухуровневый кэш (L1 Redis `bot:hash:<hash>` -> L2 PostgreSQL `Bot` + `Subscription`).
- При падении Redis резолвер прозрачно обращается напрямую в PostgreSQL с логированием `warn`.

### 5.2. AsyncLocalStorage и BotPool
- В едином процессе Node.js обработка запросов защищена через `AsyncLocalStorage<ResolvedBot>` в `apps/server/src/gateway/bot-pool.ts`.
- Входной апдейт оборачивается в `metaStorage.run(effectiveMeta, ...)`.
- В middleware контекст `ctx.botMeta` привязывается к текущей асинхронной ветке.
- Сессии grammY хранятся в Redis по изолированному составному ключу:
  `sess:${botId}:${tgId}`
  Клиент, общающийся с двумя разными ботами платформы с одного Telegram-аккаунта, имеет два полностью изолированных состояния FSM.

### 5.3. Защита от дублей вебхуков и SLA ответа 50 мс
- Ответ HTTP 200 `{ ok: true }` отправляется сервером Telegram **до начала выполнения бизнес-логики бота** (типичное время ответа 10–25 мс).
- Защита от повторной доставки апдейтов Telegram:
  1. **L1 (Redis):** ключ `upd:${botId}:${updateId}` с TTL 900 с через команду `SET ... NX`.
  2. **L2 (PostgreSQL WebhookInbox):** уникальный индекс `@@unique([botId, updateId])`. При повторе запрос немедленно завершается ответом 200 OK.
- Обработка апдейта выполняется асинхронно через `WebhookInbox` с арендой (lease lock) на 30 секунд и защитой сессии пользователя замком `lock:session:${botId}:${userId}`.

## 6. Механизмы защиты от гонок и овербукинга (QuickBook)

Для бронирования свободных интервалов времени реализована двухфазная защита:
1. **Фаза 1: Распределенный UI-лок в Redis (`slot-lock.ts`):**
   - При клике на время бот блокирует ключ `lock:slot:${botId}:${staffId}:${tsSec}` на 60 секунд.
   - Захват и освобождение осуществляются через атомарные Lua-скрипты, учитывающие составные временные интервалы услуги (например, 60-минутная услуга блокирует два 30-минутных интервала).
2. **Фаза 2: Транзакционная фиксация в PostgreSQL (`booking-service.ts`):**
   - Интерактивная транзакция с получением `pg_advisory_xact_lock(hashtext('botId:staffId'))`.
   - Проверка пересечений диапазонов: `slotTime < newEndTime AND endTime > newStartTime`.
   - Частичный уникальный индекс: `booking_slot_active_uq` по `(botId, staffId, slotTime)` где `status IN ('PENDING', 'CONFIRMED')`.
   - PostgreSQL GIST Exclusion Constraint: `booking_no_overlap_excl` на `tstzrange(slotTime, endTime) WITH &&`.
   - При конфликте транзакция откатывается, бот генерирует список альтернативных свободных слотов и отправляет пользователю.

## 7. Жизненный цикл подписок, биллинг и анти-фрод

### 7.1. Автомат состояний подписки (Subscription FSM)
- `TRIAL`: 3 дня бесплатного периода при создании бота.
- `ACTIVE`: подписка оплачена до даты `paidUntil`.
- `EXPIRED`: срок действия истек. Перевод выполняется воркером `subscription-worker.ts` через оптимистичный `updateMany`.
- `GRACE_PERIOD`: первое отклонение чека модератором при истекшем сроке.
- `BLOCKED`: повторное отклонение чека (`failedReceiptAttempts >= 2`). Подача чеков блокируется, суперадмину шлется системный алерт.

### 7.2. Анти-фрод и модерация чеков
- **Лимит ожидания:** в БД под advisory-локом запрещено создание нового чека, если у бота уже есть чек в статусе `PENDING` (`PENDING_RECEIPT_EXISTS`).
- **Валидация файлов:** проверка Magic Bytes (PNG, JPEG, WEBP). Исполняемые файлы и PDF блокируются. Лимит размера 5 МБ.
- **Транзакционный откат при отклонении:** при вызове `rejectReceipt` из `paidUntil` строго вычитается срок чека (`addMonths(paidUntil, -receipt.months)`).
- **Маскирование данных (SaaS Paywall):** в статусах `EXPIRED`, `GRACE_PERIOD`, `BLOCKED` контакты клиентов в уведомлениях и меню админа маскируются (`+998 90 *** ** 67`, `Али***`).

## 9. План проверки сквозных сценариев и граничных случаев (R3)

Для каждого сквозного сценария определен точный порядок проверки и ожидаемый результат:

1. **SCN-01: Изоляция двух тестовых бизнесов (Cross-tenant Isolation):**
   - Создать два бизнеса (Tenant A, Tenant B) с двумя разными ботами (Bot A, Bot B).
   - Попытка через API с правами/инвайтом Bot A запросить или модифицировать сущности Bot B (заявки, настройки, чеки).
   - *Ожидаемый результат:* 403 Forbidden или 404 Not Found, данные не утекают.
2. **SCN-02: Конкурентная гонка за один слот записи (Slot Race Condition):**
   - Два клиента одновременно отправляют запрос на бронирование одного и того же слота у одного мастера.
   - *Ожидаемый результат:* Ровно один клиент получает статус `CONFIRMED`, второй получает отказ и список альтернативных слотов. В базе ровно одна запись.
3. **SCN-03: Параллельные диалоги в одном боте и разных ботах:**
   - Один пользователь открывает диалог в Bot A (квиз) и Bot B (запись).
   - *Ожидаемый результат:* Состояния FSM в Redis (`sess:A:tgId` и `sess:B:tgId`) не пересекаются, ответы не путаются.
4. **SCN-04: Идемпотентность и повторные клики/вебхуки:**
   - Отправка одного и того же `update_id` трижды с задержкой 100 мс.
   - *Ожидаемый результат:* Первый запрос обрабатывается, два последующих получают ответ 200 OK `{ duplicate: true }`, бизнес-логика не дублируется.
5. **SCN-05: Поведение старых кнопок после смены конфигурации бота:**
   - Пользователь находится на шаге 2 квиза; администратор в админке меняет шаблон или удаляет опции; пользователь кликает на старую инлайн-кнопку.
   - *Ожидаемый результат:* Бот корректно обрабатывает ошибку неактуального шага (отправляет уведомление о смене меню и предлагает начать заново), процесс не падает.
6. **SCN-06: Неверный ввод и валидация данных:**
   - Отправка нечисловых телефонов, текста вместо даты, команд вне очереди, файлов с поддельными расширениями (.exe переименованный в .png).
   - *Ожидаемый результат:* Отклонение валидатором Zod / Magic Bytes с понятным сообщением об ошибке на выбранном языке.
7. **SCN-07: Ошибки Telegram API и недоступность зависимостей:**
   - Эмуляция блокировки бота пользователем (`403 Forbidden: bot was blocked by the user`), разрыв соединения с Redis при активном вебхуке.
   - *Ожидаемый результат:* Webhook отвечает 503 или 200 в зависимости от стадии, воркер напоминаний переводит в dead-letter после 3 попыток, процесс не падает с unhandled exception.
8. **SCN-08: Подключение, переподключение и смена токенов:**
   - Ввод неверного токена; попытка зарегистрировать один токен дважды; отзыв токена и обновление в карточке бота.
   - *Ожидаемый результат:* Ошибка 400 Bad Request при невалидном токене, 409 Conflict при дубле, инвалидация инстанса в `BotPool` при обновлении.
9. **SCN-09: Роли, сессии, экспирация JWT и логаут:**
   - Истечение 15-минутного Access токена, автоматический refresh через HttpOnly cookie; вызов `/logout`; попытка доступа после отзыва прав `isAdmin=false` в Telegram.
   - *Ожидаемый результат:* Бесшовный refresh в админке, немедленная блокировка действий в Telegram при снятии прав админа.
10. **SCN-10: Полный цикл подписки и модерация чеков:**
    - Истечение TRIAL (3 дня) -> маскирование контактов -> выбор тарифа -> подача чека -> отклонение (GRACE_PERIOD) -> повторная подача -> повторное отклонение (BLOCKED) -> ручное продление и разблокировка суперадмином.
    - *Ожидаемый результат:* Корректное выполнение всех переходов FSM, математически точный откат срока, уведомления в Telegram.

## 10. Требования для проверки через реальный Telegram

Для проведения live-тестирования в реальной инфраструктуре Telegram требуются следующие внешние ресурсы:
1. **Тестовые боты:**
   - 2 зарегистрированных бота в `@BotFather` с валидными токенами: один для LeadCatch (`DEV_LEADCATCH_TOKEN`), один для QuickBook (`DEV_QUICKBOOK_TOKEN`).
   - Настроенное имя, username, описание.
2. **Публичный HTTPS туннель (при тестировании вебхуков):**
   - Утилита `ngrok`, `cloudflared` или собственный VPS с SSL-сертификатом для проксирования вебхуков Telegram на локальный порт `8000`.
   - В качестве альтернативы в проекте поддержан режим `BOT_MODE=polling` (`pnpm dev:bot`), не требующий белого IP.
3. **Telegram-аккаунты:**
   - Минимум 2 физических Telegram-аккаунта (или аккаунт + тестовый клиент через MTProto/Telethon) для проверки одновременных диалогов и гонки бронирования.
   - Один аккаунт выступает в роли администратора бизнеса (активирует инвайт `adm_<code_>`), второй — в роли клиента.
4. **Статус независимости проверок:**
   - В отсутствие реальных токенов и туннеля все сценарии Telegram-логики проверяются через статический анализ кода, модульные тесты и специализированные проверочные скрипты на базе grammY Context / MockTransport.
